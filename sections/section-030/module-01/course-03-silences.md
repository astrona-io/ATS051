# Silences

A silence tells Alertmanager not to send notifications for alerts that match it during a time window. Operators create silences for planned maintenance, for a known fault that is already being fixed, or for a noisy alert while a rule is repaired. A silence changes only the notification. The alert stays in the system and its state does not change.

## What A Silence Contains

A silence is an object stored by Alertmanager with these fields.

- `matchers`: a list of label matchers with the same four operators as routes (`=`, `!=`, `=~`, `!~`). All matchers must match for the silence to apply.
- `startsAt` and `endsAt`: the time window. Alertmanager has no silences without an end time.
- `createdBy`: the name of the person or tool that created it.
- `comment`: the reason. Alertmanager requires both fields so the silence can be audited.
- `id`: a unique identifier generated by Alertmanager.

A silence has one of three states. It is pending when `startsAt` is in the future, active while the current time is inside the window, and expired after `endsAt` or after someone expires it by hand. Expired silences stay visible for a retention period and are then deleted.

## What Happens To A Matching Alert

When an alert arrives, Alertmanager compares its labels with all active silences. If at least one silence matches, the alert is marked suppressed. The API shows this in the alert's `status`: the `state` field is `suppressed` and the `silencedBy` list holds the silence identifiers. The alert is still received and still counted. Prometheus does not know about the silence and keeps sending the alert.

During notification, Alertmanager removes silenced alerts from the group before it sends. If every alert in a group is silenced, the group sends nothing. If only some are silenced, the notification contains the rest. When the silence expires and the alert is still firing, the alert becomes active again and a notification follows on the normal timers.

## Silences Are Evaluated After Routing

The order inside Alertmanager is: receive alert, route and group, then apply silences and inhibition when the notification is built. Routing therefore still happens for a silenced alert, and the alert is still present in its group. A silence cannot change the receiver of an alert, and it does not stop the alert from appearing in the alert list.

## Writing Matchers

Use the smallest set of labels that identifies the target. A silence with `alertname="ProbeErrors"` hides that alert for every service. A silence with `alertname="ProbeErrors"` and `service="probe"` hides it only for one service. A silence with only `severity="warning"` hides every warning in the system, which is almost never intended.

A silence matches the alert's labels at the time the alert arrives. A silence cannot match annotations. A regular expression matcher such as `instance=~"web-.*"` is anchored, the same as in routes.

## Creating A Silence

The v2 API accepts a POST to `/api/v2/silences` with a JSON body. The matchers are objects with `name`, `value`, `isRegex` and `isEqual` fields. The response contains the new `silenceID`. The command line tool `amtool` builds the same request from a matcher string.

Save this as `silence.py`:

```python
import json, subprocess, datetime

def in_shuttle(code):
    result = subprocess.run(['kubectl', '-n', 'starfleet', 'exec', 'shuttle', '--', 'python', '-c', code],
                            capture_output=True, text=True, timeout=30)
    return result.stdout.strip()

now = datetime.datetime.now(datetime.timezone.utc)
silence = {
    'matchers': [{'name': 'alertname', 'value': 'ProbeErrors', 'isRegex': False, 'isEqual': True}],
    'startsAt': now.isoformat(),
    'endsAt': (now + datetime.timedelta(minutes=10)).isoformat(),
    'createdBy': 'learner',
    'comment': 'practice silence',
}
code = '''
import json, urllib.request
body = json.dumps(%s).encode()
request = urllib.request.Request("http://alertmanager:9093/api/v2/silences", data=body,
                                 headers={"Content-Type": "application/json"})
print(urllib.request.urlopen(request, timeout=8).read().decode())
''' % json.dumps(silence)
print(in_shuttle(code))
```

Run it:

```sh
python3 silence.py
```

The printed JSON holds the `silenceID`. Submit an alert named `ProbeErrors` to the alerts path, then read the alert list with a GET on `/api/v2/alerts`. The matching alert has the silence identifier in `status.silencedBy` and the state `suppressed`. The webhook on the `probe` service stores no new notification for it.

## Expiring A Silence

A DELETE on `/api/v2/silence/<id>` expires the silence at once. An expired silence cannot be reactivated. To change a silence, post a new one with the same `id` in the body. Alertmanager expires the old version and creates a replacement.

## Operating Silences Safely

- Give every silence a short end time and a comment that names the reason and the owner.
- Match the alert by name and by the label of the affected target, not by severity alone.
- Review the list of active silences during an incident. A forgotten broad silence hides real failures.
- Restrict write access to the Alertmanager API, because a silence reduces visibility without changing any application.

Silences are stored by each Alertmanager instance and shared with peers in a cluster. When Alertmanager restarts without persistent storage, its silences are lost unless a peer still holds them.

## Common pitfalls

> [!WARNING]
> A silence does not fix anything. The alert still fires, the series are still bad and Prometheus still evaluates the rule. A silence with too few matchers hides unrelated alerts. A silence expires on its own, so a long fault needs a new silence or a real fix.
